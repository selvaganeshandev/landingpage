Correction to what I told you earlier

I said the database could not store a second run of a prompt. That was wrong, and it changes the plan in our favour.

PromptAnalytics can only hold one row per prompt/platform/region — that part was right. But there is a companion table, PromptAnalyticsRun, which is append-only, one immutable row per run, and the engine already writes to it on every run (prompt_analytics_processor.py:831). It stores mention, position, sentiment, the full citation list and competitors, keyed by timestamp — so multiple runs of the same prompt already fit.

Multi-run sampling therefore drops from "schema migration" to "add a repeat loop and read the table". The Runs screen moves from a big build to a medium one.

The one thing to decide first

Multi-run changes what every existing number means. A customer's visibility score will move the day it ships, because it stops being one lucky answer and starts being a rate. Decide now whether historical figures get recalculated or whether there is a clean break with a dated note — and tell customers before it happens, not after.

Effort figures assume one full-stack developer per item and include testing, not design. Every "we already have" claim was checked against the working tree on branch Selva-Ganeshan — models, processors and requirements files — not against documentation. Items 16 and 17 carry the most estimate risk because parts of them are undefined in the prototype itself.
